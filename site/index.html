Positioning

One layer, done completely — not a platform that does everything a little.

The hard, unglamorous problem isn't writing an agent — it's operating it: getting it deployed reproducibly, keeping it scoped, proving it isn't quietly hallucinating, and knowing when to roll it back. ARIA owns exactly that band of the stack and nothing else.

The open stack

Every layer is open source. The one paid dependency is swappable.

A platform you can't take apart is a platform you don't own. ARIA's entire operating stack is open and CNCF-aligned — the only proprietary piece, the model itself, sits behind an open API so it swaps for a self-hosted one without touching anything else.

Why it's built this way

Four commitments, each a deliberate reaction to how these platforms usually go wrong.

01

Own every layer

The whole operating stack is open source and self-hostable. The usual path — bolting together a dozen paid SaaS products — buys speed and sells your ability to ever fully own or audit the thing.

02

Governed by construction

Enforcement in the platform, not a policy PDF: cryptographic identity at the mesh (per-agent SPIFFE + mTLS + allow-lists — an agent is reachable only by who's authorized, by identity not network position), an eval gate (answers checked against real tool evidence, in CI), and a human approval gate (a mutating tool call is physically held until someone says yes). Admission-time policy (Kyverno) is next.

03

Reproducible, not clicked

Every agent, policy, and piece of infra is git-declared and ArgoCD-synced. There is no console-clicking path to production — the cluster is whatever the repo says it is.

04

Focused, not sprawling

One band of the stack — deploy and operate — covered end to end. Not eighteen half-finished domains on a roadmap slide.

What runs on it

Thirteen agents, grouped by what they're allowed to do.

ARIA doesn't rebuild every Kubernetes specialist — kagent already ships expert agents for Helm, Istio and PromQL. ARIA adds the governed, orchestrated agents on top, and tiers them by blast radius: an agent's tier decides which tools it may be wired to at all.

Read-only
4 agents — Kubernetes, AWS control plane, cost, git drift. Every mutating tool stripped out, not merely discouraged.
Orchestrator
1 agent — holds no tools of its own; its five delegates are its tools.
BYO
2 agents — LangGraph and Strands, the same container contract proven by two different frameworks.
Propose
1 agent — writes Terraform to a branch and opens a PR. Never touches the running environment.
Mutating
1 agent — the only one that can change the cluster, reversible tools only, every mutation held for a human.
Built-ins
4 kagent stock experts, unmodified, delegated to where raw domain expertise is enough.

Per-agent detail — tiers, engines, and the exact tools and credential scopes each one reaches — is on the fleet page.

The trust loop

An LLM answers with a 200 OK whether it's right or wrong. So we check.

Every agent answer is graded not on whether it sounds right, but on whether its claims trace back to the tool calls it actually made — a groundedness gate, wired into CI. It isn't theoretical. On its first real run it caught a genuine bug:

Caught in eval · fixed · verified

A "read-only" agent confusing its own name for a namespace

The diagnostics agent reported a connectivity check as failed — and its answer matched what the tool returned, so a text-only check would have passed it. But the grounded check saw how it called the tool:

# what the agent actually invoked k8s_check_service_connectivity({"namespace":"cluster-diagnostics", ...}) # ↑ that namespace doesn't exist — it passed its own agent name. # the "failure" was a false negative, reported with full confidence. → root cause: its prompt never told it which namespace it runs in. → one-line fix, re-run, confirmed green.

Eval-gated progressive delivery

Where this is heading: the trust loop and the deployment pipeline become the same loop. A new agent version canary-deploys to a slice of real traffic; its groundedness scores are measured live; it promotes only if it holds the bar, and rolls back if it doesn't — no human watching a dashboard at 3am to make the call.

Honest status: one half of this exists. The eval gate grades groundedness in CI today. The delivery half doesn't — Argo Rollouts isn't installed on the cluster, so there's no canary to measure and no promotion to gate. Both the progressive-delivery mechanism and the join to the eval score are still ahead, not shipped.

Honest status

What's real, what's next, what's deferred.

A solo build, kept honest. Shipped means running on a live cluster today; the rest is sequenced, not sold.

Shipped

  • Multi-agent fleet 13 agents across five tiers — read-only, orchestrator, two BYO loops, propose, mutating
  • Identity plane Istio ambient: per-agent SPIFFE + mTLS + authz allow-lists, deny proven live
  • Approval-gated remediation mutations physically held until a human says yes
  • Self-hosted MCP tool layer kmcp: AWS, GitHub and Terraform-registry servers, per-server identity allow-lists
  • Long-term memory pgvector in-cluster — no SaaS vector DB
  • Continuous eval gate groundedness-checked, in CI
  • FinOps agent live AWS Pricing, self-dogfooded
  • GitOps secrets ESO + AWS Secrets Manager, out of Terraform
  • Full GitOps delivery Terraform + ArgoCD, two layers, no manual helm
  • OTel → Langfuse tracing declarative & BYO agents
  • In-cluster CI runner self-hosted, ephemeral
  • Control-plane upgrade, for real 0.9.10 → 0.10.0-rc1 on the live fleet
  • Model gateway, fleet-wide self-hosted LiteLLM in front of Bedrock — all 11 declarative agents through it, with its own Postgres

Next

  • Agent template chart render agents, stop hand-authoring YAML
  • Kyverno admission policies governance at deploy time
  • Eval-gated rollouts join the eval gate to progressive delivery
  • Gateway routing + budgets a smart-router ModelConfig exists; cost/sensitivity routing and virtual keys are not wired yet
  • Self-service front door Backstage template built, not yet run live
  • Third BYO framework LangGraph and Strands both running; Claude Agent SDK next

Later

  • Least-privilege RBAC the real boundary under tool scoping — still the honest gap
  • Kernel-level isolation both runtimes installed and tested; neither's headline claim held up
  • Red-team scenarios refusal & injection resistance
  • Agent registry / catalog curate what's deployed
