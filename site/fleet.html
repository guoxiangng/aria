The fleet

Thirteen agents, four tiers, and what each one is allowed to touch.

Tiers are ARIA's own classification, not a kagent concept — an agent's tier is a statement about its blast radius, and it determines which tools it may be wired to at all.

The tier isn't decoration. 1-readonly agents have no mutating tool in their toolNames at all — the capability is absent, not merely discouraged by a prompt. 2-propose exists because neither existing tier described infra-author: it writes, but only to a git branch, so the blast radius of a wrong answer is a PR someone closes.

Tool layer

Seven MCP servers, each with its own credential scope.

A tool call is a network call to a separate workload holding its own credential. So an agent's real authority is its tool server's authority — which is why these are scoped individually rather than as one shared tool plane.

Why two GitHub servers. Six agents depend on the github PAT being read-only. Widening it would leave a toolNames list as the only thing between a read-only agent and pushing commits — one layer where there are currently three. Write reach got its own server, its own token, its own rotation. The credential is the control, not the prompt.

Model access

Every declarative agent reaches its model through one in-cluster gateway.

Fleet-wide since September, and not by choice: the Azure OpenAI resource behind the original shared ModelConfig was deleted, which took every declarative agent down at once. The gateway migration that followed is why there is now a single place to change a model, route by cost, or attribute spend.

The gateway runs with its own Postgres, so virtual keys and budgets are now possible where v1 was DB-less. An agent also needs its ServiceAccount on the gateway's mesh allow-list, or it is reset at the mesh before it ever reaches a model — the tool-list and the allow-list have to move together. The two BYO agents bypass the gateway entirely; they own their own model calls.
